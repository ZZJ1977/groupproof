# GroupProof 课程项目结项报告专业写作规范（Skill v1.0）

## 1. 目标读者与文档定位
- **直接读者**：高校软件工程课程任课教师、助教与课程答辩评审专家。
- **核心评估维度**：需求范围是否清晰受控、工程架构与协作机制是否落地、迭代进度是否持续稳健（非期末突击）、交付宣称是否有可复核证据支撑、成员分工与贡献是否真实公平、团队对缺陷与局限的复盘是否客观诚实。
- **文风定位**：正式、克制、严谨的高校软件工程结项技术文档，兼顾学术表达规范与工程实证密度。

## 2. 禁用套话黑名单（严格遵守）
以下空洞 AI 营销语、公文套话或情绪化夸大词**严禁出现**在报告任何章节中（出现任何一词即视为不合格）：
- 禁用概念空词：`全链路闭环`、`三大痛点`、`四大痛点`、`赋能`、`抓手`、`矩阵`、`生态闭环`、`组合拳`、`顶层设计`、`降本增效`、`深度融合`、`全面领跑`、`亮点纷呈`、`强力驱动`、`精准发力`。
- 禁用夸大结论词：`显著提升`、`大幅提升`、`大幅优化`、`明显改善`、`完美收官`、`圆满落幕`、`无懈可击`、`碾压`、`全面超越`、`零缺陷`、`绝对公平`。
- **替代原则**：用具体事实与精确数字说话（例如用「任务完成 28/28 项、正式证据 123 条、合并 PR 67 个」替代「显著提升了研发效率」；用「按需求冻结→任务拆解→PR 评审→证据核验→人工确认的五步流程执行」替代「构建了全链路闭环」）。

## 3. 章节结构与论证节奏
1. **章首核心结论（强制）**：
   - 每一章开头第一行必须以 Markdown 引用块给出 1–2 句凝练结论：
     `> **本章核心结论**：<用精确数字和关键工程事实概括本章核心判断>`
   - 让评阅教师在 3 秒内扫读掌握本章核心结论与量化依据。
2. **四步论证节奏**：
   - **核心论点**：明确指出本章节回答的工程问题或评审关注点。
   - **工程设计与权衡**：说明架构分层、流程约定或技术选型的原因与取舍（为何这样做、放弃了什么方案）。
   - **具体可核验证据**：引用输入事实 JSON 中的真实项目名、模块全称、成员姓名、精确任务完成数、GitHub 仓库/提交数/PR 合并数/代码增删行数、飞书群聊消息数与具体决议标题/确认人数、正式证据与正式成果数。
   - **可验证结果与边界**：给出客观结论；遇到缺失数据、未完成项或工程局限时直接如实陈述。
3. **正文与插图自然呼应**：
   - 系统会在渲染阶段于对应章节自动注入高清矢量架构图、流程图、进度图、证据分布图与成员贡献图（正文**不要**手写图片 Markdown URL 或编造链接）。
   - 在正文中自然引用图表语义（例如「如图 1 所示，系统在前端呈现层、核心业务模块层与外部集成基础设施层之间保持了清晰的职责隔离……」「结合图 2 所示的研发协同流程可见……」「由图 5 的多维成员贡献对比可知……」），使图文互为印证。
4. **客观冷静与局限披露**：
   - 严格区分「已完成并经证据核验的功能」与「后续可继续完善的方向」。
   - 第七章必须结合真实活跃/历史风险与飞书阻塞排查记录，客观交代当前实现边界（如高并发压测覆盖、外部平台断网降级、自动化端到端回归深度等），提出 4–5 条具体可执行的改进建议。

## 4. 严格事实与排版纪律
- **100% 事实忠实**：所有数字、人名、仓库名、模块名、任务标题、日期、飞书决议必须严格来自输入的工程事实 JSON；严禁编造任何未出现的数字、百分比、人名或测试指标。
- **不重复章级标题**：每个章节键的值直接从 `> **本章核心结论**：...` 开始，**不要**在正文开头重复写 `# 一、...` 或 `## 一、...`。
- **结构化呈现与篇幅收敛**：每章包含 `> **本章核心结论**：...`、2–3 个凝练的实质性自然段、`###` 子标题、以及 1–2 个精炼的 GFM Markdown 表格或要点列表（单表不超过 8 行，避免逐条流水账）。**每章正文严格控制在 700–1,200 中文字符**（全篇 7 章合计约 **7,000–9,500 字**），简洁有力、重点突出，严禁无节制铺陈导致冗长或输出截断；每章结尾必须语义完整、标点闭合。
- **第六章（成员贡献）特别纪律**：严禁在章首输出“尚未冻结贡献快照”等内部告警语；直接面向教师呈现多维贡献对比表与每位成员的独立交付评述；若当前快照为草稿，仅在章节最末行用斜体脚注说明：`*（注：当前基于最新贡献快照 vN 编制，正式归档前将完成团队冻结确认。）*`。
