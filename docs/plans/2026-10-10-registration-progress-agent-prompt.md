1. 基本资料（必填）
2. 学校邮箱（必填）
3. 身份确认（学生/教师）（必填）
4. 账号安全（可选）

将“完成 / 教师审核”统一改为“身份确认（学生/教师）”；第3页标题、面包屑和相关说明同步调整。第4项及对应页面统一使用“账号安全”，明确标注“可选”。页面路由可以沿用原来的 `/account/status` 和 `/account/security`。

每一项都为整条导航条目设置底色，不能只改变小图标背景：

| 阶段情况 | 条目背景 | 辅助状态 |
|---|---|---|
| 前三项中已完成的阶段 | 浅蓝色 | 勾选图标 + 已完成 |
| 前三项中未完成、跳过或尚未通过的阶段 | 浅红色 | 待完成；教师可具体显示审核中/未通过 |

| 账号安全已完成 | 浅蓝色，配蓝色完成标识 | 已完成 |

沿用/补充语义化 Tokens，可参考浅蓝 `#EAF2FF`、浅红 `#FEF2F2`、浅灰 `#F3F4F6`，确保文字对比度。当前选中页面通过边框、侧线、字重及 `aria-current="page"` 区分，不能把“选中”自动变成“已完成”。加载中使用中性占位；读取失败显示重试，不能把未知状态直接标为完成。

### 3. 完成条件与可选账号安全

阶段状态来自后端真实事实，不能按浏览顺序、点击次数、表单本地输入或 localStorage 推断：

- 基本资料：必填内容已通过后端校验并成功保存，以当前 `profileComplete` 等事实为准。
- 学校邮箱：当前绑定的学校邮箱已验证，不能只看验证码已发送或邮箱已填写；换绑等导致验证失效时必须更新状态。
- 身份确认：学生由后端确认符合学生准入条件；教师必须有针对当前资料与邮箱依据的有效审核批准。提交申请、看到状态页或客户端选择“教师”不算完成。保留学校实名核验与邮箱控制权的区分，不新增未经确认的学校规则。
- 账号安全：作为可选安全管理，不计入必填注册进度，也不阻碍合法用户进入。按后端真实安全事实判断完成；对当前密码账户，已有可用密码凭据且登录邮箱已经实际验证即可显示完成，即使这些条件是在注册时满足的。修改密码、绑定 Google 等操作自愿，不要求用户为点亮此项再改一次密码。纯 Google 账户沿用其可信认证事实，不强制创建密码。

“账号安全可选”不等于取消账号认证本身。登录邮箱归属验证仍属于既有注册/认证流程；如历史账户必须补验，应在其登录或恢复流程明确处理，不把第4项暗中重新变成新用户的必填步骤，也不能凭未经验证的邮箱接管历史账户。

建议集中派生 `profileComplete`、`schoolEmailVerified`、`identityConfirmed`、`securityComplete`、`requiredCompletedCount` 和 `canEnterWorkspace`；这些可以复用/扩展当前 DTO，无须重复建设用户库。`requiredCompletedCount` 只统计前三项，总数是3；`securityComplete` 不参与准入条件。

### 4. 注册状态文案

“注册进度”区域底部的状态文案随当前事实更新：

- 资料未完成：待完善基本资料。
- 资料已完成、学校邮箱未验证：待验证学校邮箱。
- 教师尚未通过身份确认：按实际状态显示待提交、审核中或审核未通过。
- 前三项全部完成：明确显示“完成注册”，使用完成态样式，不再保留黄色“待完善基本资料”。

侧栏与第3页主内容区保持一致；资料保存、邮箱验证和审核变化后及时重新读取并同步。教师等待审核时提供刷新入口，并在页面重新获得焦点时更新。刷新页面、退出后再登录、切换四个页面，都应得到同一份持久化状态。保留账户停用、会话失效等真实异常提示，不能用“完成注册”覆盖异常。

### 5. 新增“登入”按钮

在左侧“注册进度”区域，当前状态提示的正下方新增主按钮，简体中文文案按用户要求为“登入”。它的作用是从受限个人中心进入业务工作区，无需用户再输入一次密码。

- 前三项任意一项未完成：灰色，真实 `disabled`，鼠标和键盘均不能触发进入；旁边说明尚缺哪项。
- 前三项全部完成且当前账号认证有效、账户未停用：绿色、白色文字，可点击。即使账号安全仍为灰色“可选”，按钮也应可用。
- 点击后显示“正在进入…”，防止重复提交；后端重新核验资格，必要时将 onboarding 会话升级/轮换为 full，再进入服务端允许的业务首页或经过校验的站内 returnTo。
- 当前实现的 `/api/v1/auth/session/refresh` 需要重点检查：如果后端轮换了会话，必须把新的 HttpOnly 会话 Cookie 正确写回浏览器，并同步最新 CSRF token；不能只返回 JSON 后继续使用已失效的旧 Cookie。复用已有机制并补齐所需环节。
- 审核或账户状态已经变化时，保持在个人中心，更新状态并解释原因；网络失败可重试；会话已失效时引导重新认证。
- 不通过仅 `router.push`、放宽 API 门禁、强写 active 或前端角色变量完成进入。业务页和接口继续校验资源权限。

### 6. 一致性、语言与实现边界

让四个页面共用同一份按用户隔离的注册状态来源；保存、验证码验证、审核刷新和进入操作后更新相关 query/session 数据。用户切换和退出时清理相应缓存，避免沿用上一用户的注册进度。

全部新文案覆盖简体、繁体、英文，保留既有语言选择与偏好。补齐 `account.status.basis.password_auth` 等实际使用的词条，界面不得出现原始翻译 key。使用现有组件和 Tokens，不重做无关业务页面。

### 7. 必须通过的验收

1. 仅切换页面或跳到第3页，不会使前三项自动变蓝。
2. 基本资料保存成功后仅其对应完成项变蓝；学校邮箱真实验证后对应项变蓝。
3. 学生满足前三项后显示“完成注册”，登入按钮为绿色；账号安全可选未完成仍能进入。
4. 教师审核中或被拒时，第3项保持浅红且有具体状态，登入按钮灰色；有效批准后变蓝并允许进入。
5. 第4项未完成/跳过为浅灰可选，满足真实完成条件后为蓝色；不要求为了完成注册而修改密码或绑定 Google。
6. 后端导致资料、学校验证或审核失效时，阶段状态、总状态和按钮同步退回，不展示过期的完成结果。
7. 点击登入后，实际业务页面和受保护 API 均可正常访问；验证会话轮换后 Cookie/CSRF 同步，不出现跳回登录页或403循环。
8. 未完成、停用、会话失效的账户不能通过直链、请求伪造或按钮样式绕过权限。
9. 刷新、跨页、退出重登、不同用户、三语、360px窄屏、200%缩放及键盘操作均保持正确状态与可用布局。
