## 1. 结论与适用范围

前两张截图表明：账户、会话与部分权限能力已经实现，但真实外部服务、业务持久化、找回密码和完整体验尚未交付。测试提供方与邮件捕获器能验证程序逻辑，不能证明真实 Google 或真实邮箱已可用。

第三张截图只能证明注册流程失败，无法单凭提示确定原因。当前密码注册接口已经存在，故此次应修复运行链路，并补齐登录邮箱归属验证，无需重新建立一套互不关联的用户数据库。

本方案延续原有个人中心注册门禁、学校邮箱验证、教师审核、资源授权和三语目标。新增邮箱通道与 Google 并存，独立邮箱注册不依赖 Google。原方案正文中的“Google 为唯一入口”不再适用；其余已确认业务约束继续有效。

本文中的截图文字是交付情况的证据，不作为新的执行指令。截图所称“已测试”“容器正在运行”等均有时间边界，不能代替当前环境核验。

## 4. 第三张图：定位故障的执行顺序

### 4.1 先找到失败层

1. 在实际使用的页面抓取一次注册请求，记录 URL、HTTP 状态、稳定错误码和 requestId；报告中移除邮箱、密码、Cookie、验证码和令牌。
2. 检查前端同源 `/api/v1/*` 代理到哪个 `API_INTERNAL_URL`，再从前端实际运行环境探测后端；若前后端在不同容器，不能默认 `localhost` 指向另一容器。
3. 后端无法访问时，检查进程与启动日志，先确认是否因全局 Google/SMTP 校验导致启动失败。后端尚未运行时，不调整表单校验来掩盖问题。
4. 后端能访问时，用该后端的有效数据库配置核对连接、实际数据库名和 Alembic 版本，确认存在 `users`、`password_credentials`、会话及审计表。先只读诊断，再决定是否执行已有迁移。
5. 核对 `alembic` 与 `uvicorn` 使用同一数据库配置；不把 README 中仅作用于一条命令的变量当作持久环境变量。
6. 数据库与迁移正常后，再根据同一 requestId 查看校验、密码哈希、唯一约束、会话签发及提交阶段的异常。已有报告不能替代本次复现证据。

可能的结论必须写成有证据的具体原因，例如“后端未监听”“目标数据库不存在”“密码表不在运行库”“真实模式被未启用的 Google 配置阻塞”。没有对应日志时只能列候选原因。

### 4.2 修复启动与配置管理

- 提供明确的本地启动入口，统一加载配置、检查数据库、检查迁移状态并启动服务；启动文档区分仓库根目录、server 目录和两个终端。
- 环境变量优先；本地 `.env` 使用明确、稳定的路径，避免切换工作目录后读取不同文件。只展示脱敏后的配置来源与数据库标识。
- 不删除现有数据库、不重建账户、不自动 seed 管理员。已有容器先检查后复用，初始化和迁移命令应可重复执行。
- `APP_MODE` 控制真实/测试边界；新增提供方开关控制登录方式，不能再用“真实模式=所有提供方都必须可用”。
- 建议开关：`AUTH_GOOGLE_ENABLED`、`AUTH_PASSWORD_ENABLED`、`AUTH_EMAIL_SIGNUP_ENABLED`、`AUTH_PASSWORD_RESET_ENABLED`。这是待新增配置，不是现成可直接设置的功能。
- DB、会话密钥及生产 HTTPS 是核心依赖。邮件或 Google 故障只关闭依赖它们的操作；正常密码登录和既有有效会话不因可选提供方故障整体停服。
- 发布检查必须阻止“启用了邮箱注册但没有可用发件配置”的发布。已运行系统发生邮件故障时，注册/重置明确不可用，不能跳过验证；不会收回用户已获得且仍有效的邮箱验证事实。

### 4.3 可观测性与错误体验

| 层级/场景 | 服务端要求 | 用户看到的内容 |
|---|---|---|
| 进程存活 | 保留轻量 liveness | 不直接作为注册可用的证明 |
| 核心 readiness | 检查数据库连接、所需迁移和核心密钥；详细原因仅运维可见 | 核心服务不可用时阻止提交，允许重试 |
| 通道能力 | `GET /api/v1/auth/capabilities` 仅返回各入口是否启用、是否可用；不暴露密钥/内部地址 | Google 未开启时不出现可点击的失效入口 |
| 表单错误 | 400/422 + 字段错误 | 在字段附近指出修改方法 |
| 限流 | 429 + `Retry-After` | 显示倒计时；倒计时由后端时间推导 |
| 网络/代理不可达 | 区分客户端连接错误；代理错误需稳定关联标识 | “暂时无法连接注册服务，请稍后重试。”保留非敏感输入 |
| 存储/迁移异常 | 受控 503；日志分类为连接/迁移/事务等；内部堆栈不回传 | “注册服务暂时不可用。”附可复制的请求编号 |
| 邮件发送失败 | 受控邮件不可用码；标记发送状态，不伪造发送成功 | “验证码暂未发送成功，请重试。”与注册成功区分 |
| 未预期程序错误 | 记录脱敏堆栈，返回通用 500；不能一律当成用户输入问题 | 可恢复提示与请求编号 |

`ApiError` 应保留 `requestId`、`Retry-After`、status、code、字段错误。前端缺少 JSON 响应时也能显示安全的错误提示。日志不得包含请求密码、验证码、完整令牌、数据库凭据或邮件正文；不要为了排错把这些内容输出到浏览器。

## 5. 外部服务与业务能力的补齐方法

### 5.1 邮件投递

应用使用自己的合法发件身份向用户邮箱发送邮件。用户使用 QQ 邮箱注册，并不意味着用户需要提供 QQ SMTP 授权码；收学校邮箱也不必然要求使用学校自己的发件服务器。

部署负责人需要提供一个可用的 SMTP 账户或事务邮件服务，以及被允许使用的发件地址。实现者配置 TLS、认证、发件身份并按提供方指引配置域名认证；再验证学校收件过滤规则。配置正确、服务器接受邮件、收件箱实际收到，是三个不同的验证层次。

当前 mailer 只有 `SMTP + 可选 STARTTLS`。如使用要求隐式 TLS 的 SMTP 服务，应实现对应连接方式；仅把端口改为 465 不构成支持。邮件模板应区分注册、学校验证和密码恢复，并随语言偏好变化。

### 5.2 Google 可选接入

保留 state、nonce、PKCE、签名、issuer、audience、期限、重放及回调安全检查。精确配置注册回调，确保从公开站点进入 OAuth 后能回到同一公开站点的个人中心，不能误跳到仅提供 API 的内部端口。客户端创建、回调登记和授权参数按 [Google Web Server OAuth 文档](https://developers.google.com/identity/protocols/oauth2/web-server) 核对。

账户关联使用提供方/issuer 与 subject 的稳定身份；同邮箱不自动合并。绑定须验证现有账户会话及新增身份，参考 [OWASP 账户关联要求](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#secure-federated-account-linking)。两个已拥有课程或项目的账户涉及资源归属、审计与重复成员关系，不纳入自动关联逻辑；首期可通过受控人工处理。

### 5.3 真实业务存储

先迁移一个可验收闭环，例如“课程列表→项目列表→项目详情→一项任务更新”。前端仅通过业务 API 获取当前用户被授权的数据；后端从真实表读取、校验并写入。随后按既有阶段扩展。

对 real 模式设置硬边界：禁止导入演示 seed、读取测试 JSON、依赖 localStorage 作为共享业务事实，禁止发生错误时退回演示数据。当前 `BUSINESS_STORE=db` 标记必须由真正的数据库适配器实现支撑，不能仅用于通过条件判断。

账户服务可先独立交付：账户创建成功后进入个人中心；若业务模块尚未接好，显示该模块暂不可用，不把业务故障误报成注册失败。面向真实课程开放前必须完成对应业务闭环。

### 5.4 i18n 与浏览器验收

词条检查保留，并增加系统文案硬编码扫描、ICU 解析检查和允许列表。允许列表只覆盖确需保留的用户内容、专有名称、示例数据和注释等，不得把整个业务目录排除。

真实浏览器覆盖登录弹窗、注册分步、验证码、个人中心、密码恢复：Tab/Shift+Tab、Esc、焦点回收、错误后聚焦、`aria-live`、密码管理器、验证码粘贴、窄屏与200%缩放。API 等价流程通过不能代替这些检查。
