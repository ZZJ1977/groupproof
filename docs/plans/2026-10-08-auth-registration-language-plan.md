## 1. 推荐决策与完成标准

采用 **Google 身份认证 → 个人中心完成注册 → 服务端开放业务访问** 的流程。

Google 只负责证明用户控制某个 Google 账号。平台还必须独立确认必填资料、学校邮箱及教师审核状态。首次认证成功后，允许进入个人中心的受限注册区；只有全部条件满足，才能正式进入课程、项目和其他业务页面。

| 需求 | 实施决策 | 完成标准 |
|---|---|---|
| R1：完成注册后才能正常登录并访问信息 | 服务端会话、注册状态门禁、资源权限三层校验 | 未完成注册者通过页面、直接 URL、API、文件链接均无法取得业务数据 |
| R2：移除登录页两个辅助按钮 | 登录卡片只保留 Google 登录主入口；资料和学校邮箱功能统一归入个人中心 | 登录页无“完善个人资料”“验证邮箱”按钮；首次注册自动引导，老用户在头像菜单进入个人中心 |
| R3：可选择网站语言 | 共用语言选择组件，使用现有 next-intl 实现全站词条与偏好保存 | 切换后所有系统界面同步更新，刷新和再次登录可恢复选择 |
| R1.1：建立用户数据库，记录注册信息并支持后续核验（已确认补充） | 在 PostgreSQL 中建设用户账户与注册审核模块，分别记录用户申报、验证依据、审核结果及会话 | 注册记录持久化、可恢复、可核对；后端依据当前记录决定放行；资料入库不自动等于身份核验通过 |

用户已同意将用户数据库纳入执行方案。该模块服务于 R1，与课程、项目等业务共用规划中的 PostgreSQL，通过关联表组织；具体要求见第 7 节。

以下为本方案的建议默认值，实施时可配置，不冒充已确认的学校制度：

- 首期语言：简体中文 `zh-Hans`、繁體中文 `zh-Hant`、English `en`；未匹配到支持语言时默认简体中文。
- 保留 Google 为唯一身份认证入口；首次使用同一入口自动创建待完成注册记录，不另设密码注册系统。
- 延续当前页面中的学校邮箱规则：学生 `student.must.edu.mo`；教师 `must.edu.mo` 且需管理员审核。实际学校邮箱分配规则须在上线前确认。
- 沿用项目已规划的 FastAPI、PostgreSQL 与现有 Next.js 前端。此次必须接通真实鉴权与受保护数据接口；仅有前端拦截不能满足 R1。
- 延续当前页面布局与设计变量，聚焦功能、错误恢复和无障碍，不开展全站视觉重做。

## 3. 身份、注册和授权的统一模型

### 3.1 三个判断分别负责什么

1. **身份认证**：有效服务端会话对应哪个真实用户。
2. **注册资格**：该用户是否完成必填资料、学校邮箱验证，以及所需的身份审核。
3. **业务授权**：该用户是否是目标课程/项目的成员，是否拥有本次操作权限。

每次业务访问必须同时通过：

```text
允许业务访问 = 会话有效
            AND 会话为服务端签发的 full 范围
            AND 账号未停用
            AND 注册要求已完成
            AND 对目标资源及操作拥有权限
```

前端可使用服务端返回的结果控制展示；不能通过 localStorage、URL 参数、表单、React 状态或 Google 邮箱字符串自行授予资格。具备 active 资格也不意味着能读取全站所有信息。

放行依据来自真实用户数据库。首次 Google 认证后建立待完成注册档案，后续登录按已验证的 Google 身份标识找到该档案，再读取当前注册与审核事实。档案存在、表单字段相互一致或曾经登录成功，都不能单独构成放行条件。

### 3.2 账户状态机

以下 `accountState` 由服务端根据事实字段派生，按表格顺序判断。禁止由客户端直接提交或将多个布尔值分散在页面中判断。

| 状态 | 判定 | 允许操作与去向 |
|---|---|---|
| `anonymous` | 无有效会话 | 登录、语言选择、公开说明；访问受保护页则去 `/login` |
| `disabled` | 账号已停用 | 仅账号状态说明、退出、公开帮助；业务接口拒绝 |
| `profile_required` | 任一必填字段缺失或不合法 | 个人中心资料编辑、退出、语言；默认 `/account/profile` |
| `email_required` | 当前待绑定学校邮箱未验证 | 资料更正、发送/校验验证码；默认 `/account/email` |
| `review_required` | 教师资料、邮箱有效，但尚未提交当前版本的审核申请 | 提交申请；默认 `/account/status`；仍不开放业务区 |
| `review_pending` | 教师申请已提交且资料、邮箱有效，尚未批准 | 本人资料、审核状态、退出；默认 `/account/status` |
| `review_rejected` | 教师申请被驳回 | 查看本人原因、修改材料、重新提交；默认 `/account/status` |
| `active` | 学生注册条件满足；或教师条件满足且审核通过；受管理身份满足其开通规则 | 个人中心及本人有权限的业务范围 |

实现时严格采用 `disabled → profile → email → review → active` 的派生优先级；只有存在会话才进入这一判断。教师没有当前有效批准就不能回退成 active；审核状态不会被一次邮箱验证覆盖。已激活用户仅申请更换邮箱时，旧有效绑定仍满足注册条件，不因 pendingSchoolEmail 存在就降级；第 5.2 节的教师审核依据变更规则除外。

### 3.3 角色规则

- 自助注册仅可申请“学生”或“教师”；`requestedIdentity` 是申请意向，不能直接写 `roles`。
- 学生完成资料和学生邮箱验证后，由服务端授予学生资格；组长依据具体 `Group.leaderId` 或项目 owner 判定，不能注册成全局组长。
- 教师必须先验证教师邮箱，再由真实管理员批准后授予教师资格。邮箱域名只证明邮箱范围，不能代替教师审核。
- 助教从已完成基础注册的账户中，由所属课程教师/管理员按现有规则指定，默认只读，修改权限按课程中的具体授权判断；学校邮箱要求按其基础学生/教师身份判断，自助注册不出现“助教”选项。不能直接继承 ta 演示账户的已验证状态。
- 管理员通过受控初始化/邀请流程开通，并绑定真实 Google 身份、完成资料和学校邮箱验证；不得出现公开的管理员注册入口。初始管理员开通必须可审计。
- V1 沿用现有单一注册身份；已激活用户不能在通用资料表单自由切换学生/教师。身份变更进入受控审核流程，不在此轮扩展双身份系统。
- 管理员不自动获得课程/项目全部内容；继续遵循现有治理权限。跨组只读课程公开总览、助教课程授权等既有规则继续有效。

## 4. 用户流程与页面地图

### 4.1 首次学生注册

```text
登录页 → 使用 Google 登录 → Google 授权 → 服务端验证回调
      → 建立受限会话 → 个人中心 / 基本资料
      → 保存必填信息 → 个人中心 / 学校邮箱
      → 真实验证码通过 → 服务端激活 + 轮换会话
      → 原目标页面（仍需资源授权）或首页
```

“受限会话”只允许完成自己的账号手续，不开放课程、项目、搜索结果、成员目录或通知。注册中断后再次认证，读取服务端记录恢复尚未完成的步骤。取消授权、认证失败、超时均不能进入业务区。

### 4.2 首次教师注册

完成 Google 认证、资料、教师邮箱验证后，在个人中心确认并提交教师审核申请，然后进入“教师身份审核中”。尚未提交属于 review_required。管理员批准后重新获取账户状态并轮换会话，才开放教师权限；未批准时不能通过教师页、普通首页或 API 绕过。驳回显示对本人可见的原因和修改/重新提交入口。

审核提交与更新不能仅修改前端缓存；管理员审核页面也必须使用受鉴权的真实接口。审核绑定申请版本，旧审核不能批准后来更改的身份资料。

### 4.3 老用户登录、退出和失效

- 老用户完成 Google 认证后，由服务端判断状态；active 直接进入授权目标，未完成者恢复注册，停用者显示受限状态说明。
- 退出调用服务端注销，撤销会话并删除 Cookie；客户端清理当前用户的 Query 缓存和敏感页面状态，再回到登录页。
- 会话过期返回 401 并触发重新认证；服务暂时不可用返回 503 和重试提示，不能退回 seedData，也不能反复重定向。
- 重新登录时只保留通过检查的站内 returnTo，例如 `/projects/<id>/tasks?view=board`。拒绝外部网址、`//host`、反斜杠及编码绕过；排除认证回调/退出地址。最终跳转前再次检查资源权限。
- 无课程的新用户进入真实空态；不能默认进入 `project-1` 或 `course-1`。首页应适配学生、教师、助教的已授权摘要；管理员可进入 `/admin/users`。

### 4.4 路由与边界

| 路由 | 用途 | 门禁 |
|---|---|---|
| `/`、`/login` | 公共登录/产品介绍 | 不加载工作区；已有会话按账户状态引导 |
| `/account` | 个人中心入口 | 有会话；跳本人当前步骤，active 默认到资料页 |
| `/account/profile` | 个人中心基本资料 | 有会话且未停用；只操作本人 |
| `/account/email` | 邮箱绑定、验证与更换 | 有会话且未停用；发送前需满足资料要求 |
| `/account/status` | 注册/审核/停用状态 | 有会话；只显示本人必要信息 |
| `/onboarding/profile` | 旧链接兼容 | 引导至 `/account/profile`，不能绕过会话检查 |
| `/onboarding/email-verification` | 旧链接兼容 | 引导至 `/account/email`，不能绕过会话检查 |
| `/home`、`/notifications`、`/action-items`、`/activity` | 业务入口 | active；数据限定本人及授权范围 |
| `/courses/**`、`/projects/**`、`/teacher/**`、`/admin/**` | 各业务工作区 | active + 具体资源/操作资格 |
| `/api/v1/auth/google/start`、`/api/v1/auth/google/callback` | OAuth 协议入口 | 允许匿名到达；回调必须校验完整 OAuth 事务 |
| 未知路由 | 404 | 不加载工作区，不用演示账号兜底 |

公开帮助/关于页若尚未实现，本轮不借机扩展完整帮助系统；以后新增的公开路由须显式登记。受保护路径按已知路由分类，默认拒绝业务访问，不能只用宽泛的 startsWith 绕过检查。

既有设计页 02/03 对应的新规范路由改为 `/account/profile`、`/account/email`；旧 URL 保留别名。新增系统页单独列在页面地图中，不冒充原有 56 个设计页。

## 5. 登录页与个人中心交互规格

### 5.1 登录页

```text
GroupProof                        帮助中心  关于我们  [语言选择 / 简体中文 ▾]

左侧：保留产品介绍                 右侧：登录
                                       使用 Google 登录，继续你的课程与项目。
                                       [使用 Google 登录]
                                       首次使用将在个人中心完成资料与学校邮箱验证。
                                       [学校邮箱要求说明]
                                       [隐私与授权范围说明]
```

- 完整移除登录卡片底部“完善个人资料”“验证邮箱”及分隔点；不是用 CSS 隐藏后仍留可聚焦链接。
- Google 按钮只启动真实身份认证，不再调用 `setRole` 或无条件跳首页。防重复点击，展示“正在前往 Google…”。
- 失败留在登录页，就近说明“已取消”“登录失败，请重试”或“服务暂不可用”；错误信息不展示原始 token、堆栈或内部配置。
- 邮箱要求说明保留为文字信息卡；隐私文案与现有授权规则一致，包括课程公开项目仅公开摘要的例外。
- 左侧示例卡片使用明确的展示样例，不调用受保护项目数据。
- “帮助中心”“关于我们”不是账号验证入口；本轮不把它们改成进入工作区的快捷方式。

### 5.2 个人中心

复用同一套资料/邮箱组件，依据服务端状态呈现两种模式：

| 模式 | 布局和操作 |
|---|---|
| 首次注册受限模式 | 轻量 AccountShell；显示“基本资料 → 学校邮箱 → 完成/教师审核”；仅有本人资料、语言和退出；不挂载工作区导航、搜索、通知 |
| 已激活用户模式 | 头像菜单“个人中心”进入；可修改一般资料、管理学校邮箱、语言；显示真实的认证和审核状态 |

必填资料：姓名、用户名、申请身份、学校邮箱；学生还需学号。Google 姓名可预填，学校邮箱必须明确确认；Google 邮箱与学校邮箱分开保存。

- 姓名支持 Unicode、去除首尾空白，1–80 字符；用户名建议 2–32 位字母/数字/下划线/短横线且唯一；学校邮箱按第 6 节校验。学院、头像等不作为本轮激活门槛。
- 学号不能留空；其长度与邮箱本地部分的对应关系应按学校实际规则配置，不能根据 Mock 样本臆造“固定 6 位”。
- 个人中心区分“学校邮箱已验证”和“学校实名已核验”。首期未接入学校身份系统/授权名册时，姓名和学号显示为用户申报资料，不能因资料保存或邮箱验证而展示“学校实名已通过”。该说明同步纳入三种语言词条。
- “保存并继续”成功后按服务端 `nextAction` 跳转；失败保留输入，字段旁提示；不以固定延迟当作保存成功。
- 移除首次注册中的“稍后完成并进入首页”。可提供“保存并退出”，允许以后恢复，但不开放业务访问。
- 普通资料编辑不得无条件重置邮箱验证、教师审核或账户状态。用户名冲突由数据库唯一约束兜底。
- 学校邮箱更换使用独立流程：旧已验证邮箱在新邮箱验证前继续有效；更换请求保存为 pendingSchoolEmail，失败/取消不覆盖原邮箱。新地址验证成功后原子替换。教师变更审核依据时撤销旧教师资格并重新审核，不能沿用旧批准。
- 首次注册提交邮箱后更正地址，应作废原挑战并回到邮箱待验证状态；没有旧已验证邮箱可保留。
- 不能修改只读的实际角色、Google 身份标识、verification 时间和审核结果。账号换绑另走受控恢复流程，本轮不提供任意邮箱合并账号。
- 表单有可见 label、键盘焦点、字段关联错误；验证码用单一输入支持粘贴、`inputMode="numeric"` 与 `autocomplete="one-time-code"`。切换语言保留未提交内容。

## 6. 服务端鉴权与验证方案

### 6.1 推荐架构及服务边界

```text
浏览器 ── 同源 HTTPS ── Next.js 页面 / 受控 API 转发
                              │
                              └── FastAPI：OAuth、会话、注册、权限、业务 API
                                      │
                                      ├── PostgreSQL：身份、会话、验证码、业务数据
                                      └── 邮件服务：学校邮箱验证码
```

FastAPI 是身份与授权事实的唯一服务端来源。沿用规划中的数据库，不要求为了登录单独引入 Redis/Celery；验证码计数、幂等及会话撤销必须跨进程一致，可先通过数据库事务实现。

- 浏览器统一访问 `/api/v1/*`，同源代理或 Next Route Handler 仅转发必要路径、Cookie 和响应，不提供“信任任意 X-User-Id”的捷径。
- Next 服务端获取会话以决定页面重定向；FastAPI 对每个业务请求独立鉴权。前端的判断不能代替 FastAPI 判断。
- 用成熟 OIDC 客户端处理协议，建议核对 Authlib 的 FastAPI/Starlette 适配后采用；不要手写签名验证或令牌协议。选定兼容稳定版本并锁定依赖。[Authlib 官方示例](https://github.com/authlib/demo-oauth-client)
- 本项目目前没有已落地后端目录。后续执行者若没有其他既有后端，建议在 `server/` 建立 FastAPI 服务；若真实后端已在其他仓库，则按相同契约接入并记录位置，不在两个服务重复维护身份系统。

### 6.2 Google 认证

使用服务端 Authorization Code + OIDC 流程，启用 PKCE S256，生成并校验绑定浏览器事务的 state、nonce；授权范围限定 `openid email profile`。回调地址在 Google 控制台显式登记。

服务端使用官方发现文档/JWKS 与成熟库验证签名、issuer、audience、有效期和 nonce，检查事务的一次性与超时；必要时校验 azp。以规范化的 provider/issuer + `sub` 作为外部身份唯一键，不以邮箱作为 Google 用户主键。Google 对 `sub` 和 token 校验的要求见[官方 OIDC 文档](https://developers.google.com/identity/openid-connect/openid-connect)。

- callback 重放、state/nonce 不匹配、兑换失败或用户取消，均不得创建可用业务会话。
- Google Client Secret、验证码密钥只存服务端环境变量，不使用 `NEXT_PUBLIC_*` 暴露。
- Google 的 `email_verified` 不等于本平台学校邮箱已验证；本期学校邮箱统一由本平台实际发送验证码。`hd` 参数/声明也不能直接授予教师角色。
- 不请求登录以外的长期 Google API 权限；不需要的 access/refresh token 不存储、不下发。应用会话与 Google token 分离。
- 并发首次登录通过数据库唯一约束确保只有一个用户/外部身份记录；重复 callback 不新增账户。
- 两个不同 Google 身份声称同一个学校邮箱时，不自动合并；显示可恢复的冲突提示，不透露另一个用户的身份资料。

### 6.3 应用会话与 CSRF

- 使用服务端可撤销的随机会话；客户端 Cookie 仅保存不可解释的随机 ID，数据库保存其摘要及有效期。
- 生产 Cookie 建议 `__Host-gp_session`，`HttpOnly; Secure; SameSite=Lax; Path=/`，不设 Domain；全站 HTTPS。Cookie 安全属性、会话轮换参考 [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。
- 建议默认：受限注册会话闲置 30 分钟、绝对期限 12 小时；正常会话闲置 2 小时、绝对期限 7 天；管理员闲置 30 分钟、绝对期限 12 小时。均为产品参数，不是协议强制值；由服务端执行期限。
- 首次认证、受限转 active、敏感权限变化时轮换会话并使旧会话失效；账号停用撤销已有会话。停用用户再次成功认证时最多取得仅可查看本人状态的受限会话。
- scope 取 `onboarding`、`full`、`status_only`。审核通过不会让旧 onboarding 会话直接访问业务：允许其调用 session/refresh 重查并换成 full。服务端返回的 nextAction 在需要轮换时指向刷新流程；前端在完成轮换前不挂载工作区。注册状态变差时，即使仍持有 full Cookie，也会被当前状态校验拒绝。
- 所有受保护 API 读取当前资格，或检查可靠的 authVersion；不能仅依赖登录时写入的陈旧 role。审核通过后通过重新认证/受控 session refresh 轮换，不能凭前端刷新按钮自我提权。
- 敏感邮箱换绑要求最近 10 分钟内通过可验证的重新认证，校验同一 provider/sub 并记录服务端 recentAuthAt；普通续期或只显示账号选择器不算重新认证。所选 Google 流程若不能提供相应保证，须增加向原已验证学校邮箱发送的一次性确认，作为换绑的独立前置条件。该确认仅授权本次指定目标的换绑、不直接验证新邮箱；取消或换成其他 Google 账号不得继续。二者均未落地时暂不开放换绑，保留已验证地址及正常登录能力。
- 所有普通写操作采用非 GET 方法；校验 Origin 与绑定会话的 CSRF token。OAuth 的 start/callback 是协议专用路径，使用 state/nonce/PKCE 及事务 Cookie 防护。不能把 SameSite 当作完整 CSRF 防护。[OWASP CSRF 指南](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- session 查询与敏感响应设置 `Cache-Control: private, no-store`；禁止共享 CDN 缓存、静态预渲染或全局跨用户缓存敏感 DTO。
- 退出/切换账号清理缓存并取消在途请求；查询键至少按 userId 隔离，防止旧请求在退出后写回新用户缓存。多标签页同步注销状态，返回页面及重新聚焦时重新确认会话。

### 6.4 学校邮箱验证码

1. 服务端先解析邮箱并精确匹配允许的域名；禁止用 `includes("must.edu.mo")` 或不带边界的后缀匹配。拒绝伪后缀、额外子域和控制字符；学校地址按确认的大小写规则归一化。
2. 新注册者在有效受限会话内发送验证码，目标必须是其本人保存的学校邮箱；不能通过请求替别人验证。
3. 生成密码学安全随机 6 位验证码，10 分钟有效；数据库保存带服务端密钥的 HMAC、challengeId、userId、邮箱、用途、过期时间及次数，不保存明文或仅保存可离线枚举的普通哈希。
4. 每个 challenge 最多尝试 5 次；重发冷却 60 秒；建议账号及邮箱各最多 5 次/小时、20 次/日，IP 额外较宽限制并适配校园共享出口。限制在服务端跨进程生效，返回 429 与 retryAfterSeconds。
5. 校验绑定 userId + 精确邮箱 + 用途 + challengeId；只能消费一次。重发、更改目标邮箱、取消换绑时作废旧 challenge；事务防止并发重复消费。
6. 只有邮件服务确认接受发送请求后，才提示“验证码已发送”；发送失败显示失败与重试。该确认不宣称邮件已投递到收件箱。
7. 学生验证成功后按完整注册条件激活；教师转为待提交/待审核流程，不能直接变 active。验证码成功和状态变更在同一事务提交。
8. 测试环境可使用隔离的邮件捕获器；生产禁止固定验证码、任意验证码通过和调试查询验证码接口。

随机、过期、一次性、限流等原则参考 [OWASP 一次性令牌指南](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)；上述具体数值是本方案对邮箱验证的建议，并非照搬密码重置流程。

### 6.5 真实数据保护范围

- **页面层**：公共页不挂载业务数据 Provider；受限个人中心只拿本人账户 DTO；注册达标且会话为 full 后才挂载 WorkspaceProvider。
- **接口层**：所有业务查询、搜索、统计、批量接口、通知、SSE/实时连接及写操作先做 `requireActiveUser`，再做资源授权。重连/权限撤销后也检查资格。
- **资源层**：按课程关系、项目成员、组长身份、教师所属课程、助教具体授权执行现有策略；跨组公开总览只返回既有五字段 DTO，绝不先返回全量数据再由客户端裁剪。
- **文件层**：预览/下载/导出均受同样保护。若要求停用或退出后立即失去下载能力，本轮采用每次鉴权的下载代理；普通预签名 URL 在有效期内仍可用，不能用于宣称“立即撤销”。
- **命令层**：actorId、角色、服务器时间由会话/服务端注入；保留 expectedVersion、幂等与审计语义。禁用远端通用 `update("users", patch)` 等任意字段写入接口。
- **失败行为**：匿名 401；已认证未完成注册/待审/停用 403 + 具体错误码；资源无权采用统一 404 或既有 403 策略；无关数据不得在错误体中出现。

现有 `lib/access/policy.ts` 是业务规则参照。迁移至 FastAPI 后应以同一组权限矩阵用例核对一致性，不能把客户端 can() 的返回值作为服务端证据。Next.js 也明确建议贴近数据读取执行校验，而非只检查布局或 Middleware。[Next.js 15 鉴权指南](https://nextjs.org/docs/15/app/guides/authentication)

## 7. 用户账户与注册审核模块：数据库、核验及接口

### 7.1 模块目标与数据归属

建立持久化用户数据库，记录“用户填了什么、哪些信息已验证、依据是什么、现在允许做什么”。FastAPI 负责写入和核验；前端通过限定接口读取本人所需信息。数据库连接凭据只由服务端持有，浏览器不直接执行数据库操作。

- 与课程、项目数据共用规划中的 PostgreSQL；用户档案、外部身份、验证/审核和会话分别建关联表，统一以内部 userId 关联。
- 首次认证即可保存待完成注册记录。提交成功的资料、验证结果和审核状态在刷新、换设备及服务重启后仍可恢复。
- 本期采用“学生学校邮箱验证、教师另加管理员审核”的准入规则。未接入学校身份系统或授权名册时，学生姓名、学号、学院属于用户申报资料；其真实性尚未获学校确认。
- 在数据库中保留核验来源与范围，后续可接入学校认可的身份核验，但本轮不新增学校 SSO 或导入未经授权的学生名册。
- 只保存平台所需的资料、验证和会话记录。继续 Google 登录时，不收集或保存 Google 密码；账号身份标识与学校邮箱分开管理。

### 7.2 信息合理性的三层检查

| 检查层级 | 服务端检查内容 | 结果能证明什么 | 对放行的影响 |
|---|---|---|---|
| 格式与完整性 | 必填项、长度、邮箱格式/精确域名、已确认的学号规则 | 资料符合输入要求 | 不符合则返回字段错误，不能完成注册 |
| 一致性与唯一性 | 同一 Google 身份是否已有账户、规范用户名/已验证学校邮箱是否冲突、已确认的学号与邮箱对应关系 | 记录符合约束，避免重复绑定和相互矛盾 | 硬约束冲突需解决，不能新建重复身份或覆盖别人绑定 |
| 身份真实性 | 邮箱验证码、教师人工审核；未来通过学校身份系统、授权名册或有依据的人工核验确认特定字段 | 只证明实际检查过的身份属性 | 按本期准入规则放行；没有实施的核验不能标成通过 |

学生邮箱验证只证明当前用户控制该学校邮箱，不自动证明其自填姓名、学号或在读状态。资料与自己的历史输入一致也不构成新的真实性证据。Google 认证同样不代替学校实名核验。

本期不以未经核验的学号作为登录主键，也不允许仅凭填报学号合并账户。重复的自报学号可记录为待核对问题，但不能据此认定哪个用户真实、泄露另一人的档案，或让抢先填报者永久占用真实身份。只有确认学校学号的唯一范围及可靠核验依据后，才增加相应身份绑定硬约束。

### 7.3 关联表与服务端派生视图

下列名称为实施规格，可按既有后端命名约定调整，字段语义和约束必须保留。RegistrationFacts 是派生结果，不要求额外建立一张可随意写状态的表。

| 实体 / 建议表 | 必须表达的字段/约束 |
|---|---|
| User / `users` | id、name、username、规范 username、studentId、可选 college、requestedIdentity、正式角色、accountStatus(enabled/disabled)、preferredLocale、authVersion、version、createdAt、updatedAt、lastLoginAt；尚未提交的注册字段可空，完整性由规则判断 |
| AuthIdentity / `auth_identities` | provider、issuer、subject(sub)、userId、Google 邮箱、createdAt、lastAuthenticatedAt；规范化 provider/issuer/subject 唯一，Google 邮箱不是身份主键 |
| SchoolEmailBinding / `school_email_bindings` | userId、已验证 schoolEmail 及规范值、verifiedAt、verificationMethod、pendingSchoolEmail；每人一个当前绑定，已验证规范邮箱全局唯一；待验证地址不永久占用名额 |
| AcademicIdentityCheck / `academic_identity_checks` | userId、核验字段范围及对应快照/版本、method(school_sso/authorized_roster/documented_manual_review)、result(passed/failed)、受限 evidenceRef、checkedBy、checkedAt、supersededAt；保存实际发生的实名/学籍字段核验，首期可没有记录 |
| Session / `sessions` | tokenDigest、userId、scope、authVersion、createdAt、lastSeenAt、expiresAt、absoluteExpiresAt、revokedAt；scope 不能覆盖当前资格 |
| EmailChallenge / `email_challenges` | challengeId、userId、email、purpose、codeHmac、expiresAt、attempts、consumedAt、invalidatedAt、发送状态；每个账户/用途最多一个可消费的当前挑战 |
| TeacherApplication / `teacher_applications` | userId、申请版本、审核所依据资料的快照、pending/approved/rejected、reviewerId、reviewedAt、reason；记录批准的是哪一版资料及哪种身份资格 |
| AuthAuditEvent / `auth_audit_events` | 事件类型、actorId、目标、requestId、时间、结果及必要的变更字段名；不记录 token/验证码，邮箱最小化记录 |
| RegistrationFacts / 服务端派生 DTO | profileComplete、schoolEmailVerified、teacherReviewStatus、academicIdentityStatus、verificationBasis、accountState、nextAction；全部从当前事实计算，禁止客户端写 isRegistered/active 绕过条件 |

academicIdentityStatus 可为 `unverified`、`verified`、`rejected`、`stale`；没有实际核验记录时为 unverified。该字段只表示相应实名/学籍字段的核验情况，首期学生满足资料和学校邮箱条件即可按现有规则激活，不要求额外通过尚未接入的学校实名系统。拒绝或过时的学籍核验记录应进入人工处置，不默默改变首期准入规则；确认不再符合资格时由受控停用流程处理。

verificationBasis 应说明已完成的是 Google 账号认证、学校邮箱控制权验证还是教师人工批准，不能用一个 verified 布尔值混合表达。实名核验摘要须附核验字段范围；部分字段通过不代表整份档案通过。TeacherApplication 的批准也只表示规定的教师审核已通过，不虚构学校官方核验结果。

### 7.4 数据约束、修改和读取边界

1. 主键与外键：内部 userId 由服务端生成；各关联表引用真实用户；创建 User 与 AuthIdentity 使用同一事务，避免留下无绑定的半成品账户。
2. 唯一性：规范用户名、Google 身份键和已验证学校邮箱使用数据库唯一约束兜底。用户名按第 5.2 节字符范围校验后，以去首尾空白、ASCII 小写值检查唯一；未提交时可空。邮箱按第 6.4 节确认的规则归一化，仅对已成功绑定的规范值约束。并发冲突返回可恢复业务错误，不能仅依赖“先查询有没有”。
3. 原子变更：验证码消费、学校邮箱绑定和相应资格更新一起提交；教师批准/停用与权限版本、审计同步提交。失败整体回滚，不能只写成功标记却缺少对应依据。
4. 字段来源：姓名、学号等用户申报字段可按规则编辑；验证码验证时间、核验来源、审核人/结果、正式角色和停用状态只能由对应服务端流程写入。普通资料接口采用严格字段白名单。
5. 历史依据：修改被核验的姓名、学号、邮箱等字段时，仅使依赖这些字段的核验结论失效/过时，保留旧记录和对应版本；语言、用户名等无关变更不清空已有证明。教师审核所依赖的身份资料变化仍按第 5.2 节重新审核。
6. 最小读取：个人中心只返回本人可见资料与核验摘要；管理员审核接口按治理权限返回必要记录。普通用户、同组成员及公共页面均不能读取完整用户库、审核材料、验证码摘要或会话凭据。
7. 数据权威：真实服务从数据库和可验证的服务端会话读取事实；客户端缓存只用于展示。数据库不可用时返回服务不可用，不从 localStorage、Mock 或“上次已放行”推断本次资格。

现有 `User.verified/status/teacherStatus` 不足以覆盖上述语义，应显式迁移/适配；禁止将 Mock 的 `verified: true` 导入为真实验证证据。实施交付需包含关联表迁移、字段字典、索引/约束及注册状态派生规则。

### 7.5 注册记录如何参与后续登录

1. 先由服务端验证本次 Google 认证结果，再用 provider/issuer/sub 查询 AuthIdentity，取得内部 userId；输入姓名、邮箱或学号不能直接指定要登录的用户。
2. 找不到绑定时，事务创建待注册 User 和 AuthIdentity，签发 onboarding 范围会话；已有绑定则恢复原档案，不重复创建。
3. 用户保存资料后持久化输入并完成格式/唯一性检查。资料保存成功仅表示入库成功，验证结果仍须由真实验证码或审核流程产生。
4. 邮箱验证和所需审核完成后，按第 3 节派生当前 accountState。学生可以是 `accountState=active` 且 `academicIdentityStatus=unverified`，其准入依据明确为学校邮箱验证，界面不得称其“学校实名已核验”。
5. 后续登录读取当前记录：资料缺失去资料页、邮箱未验证去验证页、教师待审/驳回去状态页、停用者受限；满足 active 条件后才签发 full 会话。已有有效验证无需每次登录重新提交，但要检查它是否仍适用于当前资料。
6. 签发 full 会话后仍按课程/项目关系做资源授权；停用、撤销及资料变更按最新记录生效，数据库中的“存在此用户”不等于业务访问许可。

### 7.6 接口表（建议公开前缀 `/api/v1`）

| 方法与路径 | 最低资格 | 输入要点 | 结果/限制 |
|---|---|---|---|
| `GET /auth/google/start` | 公开 | 经白名单校验的 returnTo | 建立 OAuth 事务并跳 Google |
| `GET /auth/google/callback` | OAuth 事务 | code、state；由库处理协议 | 验证身份、建会话并按账户状态跳转 |
| `GET /auth/session` | 公开 | Cookie | 匿名返回 authenticated=false；否则返回最小本人状态、sessionScope、nextAction、CSRF token；不返回工作区 |
| `POST /auth/session/refresh` | 有效会话 | CSRF token | 重查资格并按需轮换；不能延长绝对期限或自授角色 |
| `POST /auth/logout` | 有/无会话均安全幂等 | 有会话时校验 CSRF | 撤销当前会话、清 Cookie、204 |
| `GET /me` | 未停用的本人会话 | 无 userId 参数 | 本人申报资料、注册事实、核验来源摘要与审核状态；不返回核验材料/会话凭据；停用会话仅用 session 获取状态说明 |
| `PATCH /me/profile` | 未停用的本人会话 | 姓名、用户名、学生学号等字段白名单、expectedVersion；首次申请身份 | 只更改可编辑资料；返回新状态；身份激活后不随意切换 |
| `POST /me/school-email/change` | 未停用的本人会话 | 待绑定学校邮箱、expectedVersion；已激活账户需近期重新认证或指定目标的旧邮箱确认凭据 | 保存待验证地址并作废旧挑战；不覆盖原已验证邮箱 |
| `POST /me/school-email/challenges` | 资料达标的本人会话 | 用途；目标从服务端待验证地址读取 | 返回 challengeId、掩码邮箱、expiresAt、resendAvailableAt；不返回验证码 |
| `POST /me/school-email/verify` | 同一有效本人会话 | challengeId、code | 原子校验、更新绑定与资格、按需轮换会话 |
| `POST /me/teacher-application` | 资料/教师邮箱有效 | expectedVersion、申请材料 | 提交/重新提交待审申请；禁止重复申请形成多条活动记录 |
| `PATCH /me/preferences` | 未停用的本人会话 | preferredLocale 白名单 | 保存个人语言偏好，不能修改角色/注册状态 |
| `POST /admin/teacher-applications/:id/review` | active 管理员 | decision、reason、expectedVersion | 审核指定版本、更新资格并审计 |
| `POST /admin/users/:id/disable` | active 管理员 | reason、expectedVersion | 停用目标并立即撤销会话；保留业务历史 |
| 现有各业务查询/命令 | active + 资源授权 | 复用接口交接表中的业务契约 | 逐个迁移，禁止下发全量 MockData |

表中的学校邮箱提交独立于资料更新；首次“保存并继续”需明确保存资料及待验证邮箱，两者都成功才进入下一步，部分失败保留输入。也可提供具事务语义的注册表单接口，但不得重新引入任意字段 patch。

若使用旧邮箱确认作为换绑前置条件，应增加 `POST /me/school-email/change-authorization/challenges` 和 `POST /me/school-email/change-authorization/verify`：均要求已激活的本人会话及 CSRF；前者接受新目标地址但只向服务端读取的当前旧邮箱发码，后者校验独立用途 challenge 并签发一次性、10 分钟有效且绑定本人和精确新地址的换绑授权。它与新邮箱验证分开消费、分开限流；不能用旧邮箱验证码直接把新邮箱标成 verified。

`GET /auth/session` 示例为契约草案，示例 ID 无实际用户含义：

```json
{
  "authenticated": true,
  "sessionScope": "onboarding",
  "user": {"id": "user-example", "name": "示例用户", "preferredLocale": "zh-Hans"},
  "accountState": "email_required",
  "nextAction": {"type": "verify_school_email", "href": "/account/email"},
  "csrfToken": "session-bound-token"
}
```

统一错误体使用 `code`、可翻译参数、fieldErrors、requestId；前端按 code 翻译，不匹配中文字符串。至少覆盖 `UNAUTHENTICATED`、`REGISTRATION_REQUIRED`、`TEACHER_REVIEW_PENDING`、`TEACHER_REVIEW_REJECTED`、`ACCOUNT_DISABLED`、`FORBIDDEN`、`INVALID_CODE`、`CODE_EXPIRED`、`RATE_LIMITED`、`EMAIL_CONFLICT`、`VERSION_CONFLICT`、`AUTH_UNAVAILABLE`。fieldErrors 也用稳定错误码和参数，避免英文界面夹入后端中文。

## 8. 语言选择与全站国际化

### 8.1 组件行为

右上角静态“简体中文”替换为真实的语言选择控件：地球图标 + “语言选择” + 当前语言 + 展开标记。界面语言改变后，控件标签跟随翻译；选项始终用各语言自己的名称，便于误选后找回。

| locale | 下拉选项原文 | 备注 |
|---|---|---|
| `zh-Hans` | 简体中文 | 默认回退语言 |
| `zh-Hant` | 繁體中文 | 适合本项目澳门使用场景，术语需人工复核 |
| `en` | English | 完整英文界面 |

- 当前选项有文字/勾选状态，不用国旗代表语言。能使用 Tab、方向键、Enter、Escape；关闭后焦点回到触发器。
- 复用现有 Radix 控件与 Design Tokens。若使用 DropdownMenu，扩展 RadioGroup/RadioItem 等单选语义；无需另引一套组件库。
- 登录页、受限个人中心、正式工作区共用同一个 `LanguageSwitcher`。个人中心偏好设置读取同一状态，不创建第二套互相覆盖的语言值。
- 选择即生效，保持当前 URL、query、页面步骤、筛选和未保存表单；不要求退出/重新登录。对异步词条加载给出短暂反馈，失败保留原语言。
- 窄屏可缩短触发文案，但可访问名称仍清楚；点击目标至少 44×44px，选项不被屏幕边界裁切。

### 8.2 偏好与恢复规则

服务端解析优先级固定为：

```text
本浏览器显式语言 Cookie
    > 当前已认证账户 preferredLocale
    > Accept-Language 中最合适的受支持语言
    > zh-Hans
```

- Cookie 建议命名 `gp_locale`，仅写白名单值、有效期一年；服务端写入，使用 Path=/、SameSite=Lax、生产 Secure。它不是身份凭证。
- 浏览器自动检测只是回退，不立即保存成“用户显式选择”，避免新设备登录后覆盖已保存的账户偏好。
- 用户明确切换时立即更新 Cookie；已登录且可修改偏好时同步 `PATCH /me/preferences`。跨设备持久化失败则提示“已在此浏览器切换，账户偏好同步失败，可重试”，不伪造保存成功。
- 登录后如本浏览器已有显式选择，继续使用该选择并同步账户；无显式选择则采用账户偏好。退出保留语言 Cookie，但清除身份和业务缓存。
- 映射旧值 `zh`/`zh-CN` 为 `zh-Hans`，`zh-TW`/`zh-HK`/`zh-MO` 为 `zh-Hant`，英文区域变体回退 `en`；显式 Hant/Hans 脚本优先于地区。其他不支持值回退，不能直接用于任意文件路径 import。

### 8.3 实现方式与覆盖范围

继续使用 next-intl，采用 **Cookie/偏好驱动，不增加 `/en` 等语言路由前缀** 的方案，保留现有课程、任务和项目链接。next-intl 官方支持从 Cookie 等应用逻辑提供 locale。[next-intl App Router 指南](https://next-intl.dev/docs/getting-started/app-router)

建议结构：

```text
i18n/config.ts               支持语言、默认语言、旧值映射
i18n/request.ts              服务端解析 locale 与白名单加载词条
messages/zh-Hans.json        完整简体系统文案
messages/zh-Hant.json        完整繁体系统文案
messages/en.json             完整英文系统文案
components/language-switcher.tsx
components/app-providers.tsx 公共 i18n / Query Provider，不读取业务工作区
```

实施要求：

1. 在 `next.config.mjs` 接入 next-intl request 配置；`app/layout.tsx` 根据同一 locale 渲染 HTML lang、文档描述和 Provider。首屏服务端和客户端一致，避免先中文后英文的闪烁与 hydration 错误。
2. 将 i18n Provider 从当前 WorkspaceProvider 中拆出；登录页使用语言能力时不需要加载任何工作区数据。路由层 locale 刷新不得给表单添加变化的 key 导致重新挂载。
3. 提取全站可见系统文案：登录、个人中心、导航、全部 56 个业务页的标题/按钮/表格/空态/状态标签、对话框、校验、加载、通知模板、权限与网络错误、aria-label、原生提示及已支持的导出界面。
4. 命名空间建议 `common/auth/account/navigation/course/project/task/evidence/teacher/admin/errors`；业务 enum 与 message key 保持稳定，不使用中文显示文本作业务判断。
5. 日期、时间、数字、百分比和复数使用 next-intl/Intl 格式化。`lib/utils.ts` 不再固定 `zh-CN`；时区默认沿用项目 `Asia/Macau`，语言切换不改变同一截止时间的含义。
6. 系统生成的通知和审计显示采用事件类型/词条键 + 参数，而非提前永久存成某一种语言的句子；历史文本按原文显示并明确其历史性质。
7. 用户填写的姓名、课程名、项目名、讨论、证据原文、文件内容保持原文。切换界面语言不修改项目的内容语言、AI 输出语言或用户业务数据。
8. 三种词条的 key、插值参数和复数规则在 CI 核对；运行时缺 key 可降级简体并记录，但发布验收必须为零缺失，不接受长期混合语言或只翻译登录页。

已支持的系统导出模板若包含界面标签，应使用所选语言；此次不增加新的翻译服务或重做正式报告导出引擎。Google 授权页面的语言由 Google 控制，可传支持的语言提示，但不承诺完全由本站控制。

### P2：页面与数据访问边界

- 拆分公共 Provider、AccountShell、业务 WorkspaceProvider；接真实会话与必要页面守卫。
- 逐个迁移受保护数据查询/命令，服务端返回最小授权 DTO；现有业务契约见接口交接表。
- 关闭生产演示入口、默认用户、角色切换及假验证码；公开页和未完成注册者没有业务数据请求/内嵌数据。

**完成门槛**：未完成注册者、跨课程账号及停用账号通过 API/直链/下载都不能越权。仅前端已完成或少数 API 已接通不得计为完成 R1。

### P3：登录与个人中心闭环

- 移除登录页两个按钮，Google 成功后按 nextAction 引导。
- 注册步骤、教师待审/驳回、邮箱更换、断点恢复、真正退出、已激活空态完整可用。
- 个人中心区分资料已保存、学校邮箱已验证、教师审核已通过与学校实名核验结果，说明实际验证范围；未核验资料保持申报标记。
- 保留旧 onboarding 链接兼容，但其页面资格受统一门禁控制。

**完成门槛**：新学生、新教师、老用户、中断重进四条主流程可在浏览器走通；无“跳过注册进入业务区”。

### P4：语言与全站词条

- 建立 locale 解析、SSR Provider、共用选择器、Cookie/账户同步。
- 按入口/账号 → 公共组件 → 学生项目与课程 → 教师/Admin 顺序提取词条；每批更新覆盖清单。
- 完成日期/数字、动态错误、通知模板、无障碍文本和窄屏检查。

**完成门槛**：三种语言全部系统文案覆盖，刷新/登录恢复，切换不丢输入，不混用项目内容语言。

### P5：生产模式验收与交接

- 按第 11 节完成接口、浏览器和负面用例，记录实际命令、环境、截图/请求证据与未覆盖项。
- 更新 FRONTEND_STATUS、路由实施计划、阶段索引和接口交接表；明确哪些仍是 Mock，不能以过往 56 页 HTTP 200 代替本次鉴权验收。
- 部署前核对生产构建无 Mock 授权回退，真实 Google 和学校邮件闭环已完成，所有上线业务接口已受到保护。

**完成门槛**：三个用户目标及 R1.1 用户数据库补充要求全部达标，阻断性问题为零。仍未接服务端的模块可以留在隔离演示环境，不对真实用户宣称已具备相应受保护能力。

### 11.4 工程与证据要求

- 运行现有 `npm run lint`、`npm run typecheck`、`npm run build`，及受影响的权限/命令/业务回归检查。

## 12. 上线、迁移与未具备条件时的处理

- 真实库不从浏览器 localStorage 导入身份、verified、role 或课程权限。演示 seed 仅用于隔离测试；若有真实历史成员需迁移，建立人工可审查的账号映射并重新验证。
- 用户数据库上线前核对迁移脚本、字段字典及核验来源。真实历史资料迁移须分别标记申报字段和可追溯的已验证事实；没有证据的记录保持未核验，不能批量填充 verified 或伪造验证时间。
- 生产构建要求显式真实服务模式；配置缺失应启动失败或显示不可用，不自动打开演示。建议 `APP_MODE=real`；仅隔离开发/演示环境允许 mock，URL 参数不能切模式。
- 全站数据接口保护是上线条件。现有大量基于全量 MockData 的页面必须完成受授权 API/DTO 适配；不能把它作为“以后再做”的安全尾项。
- 功能灰度可按已授权测试账户进行；若回滚，回到仍受保护的版本或维护模式，绝不回退成可直接进入工作区的旧演示登录。
- 真实 Google 配置、学校邮件投递条件、学校域名/学号政策、初始管理员和实际后端位置应在上线记录中确认。缺少其中一项只影响对应联调，不阻止其余契约、界面和测试代码先行完成。
- 本轮不新建密码登录、全校 SSO、任意账号合并、内容机器翻译、付费身份服务或新的视觉体系；如未来需要，单独设计。
