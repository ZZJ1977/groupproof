# GroupProof 管理后台真实后端设计

## 目标

把现有 Admin 六个页面背后的治理能力从“页面可演示/部分真实接口”推进到可验证的真实服务：管理员身份由统一认证服务校验，数据由 PostgreSQL 持久化，所有有副作用的操作有 CSRF、版本校验、幂等键和审计记录；前端只展示后端实际提供的数据，不把 Mock 或 503 假装成空数据。

本次实现服务于课程项目的管理后台和最终演示，重点覆盖用户/教师治理、课程生命周期、审计、AI 用量和临时访问审批，并保持现有学生、教师、任务、证据数据契约不变。

## 已知现状

- 统一认证和业务 API 的正式入口是 `services/api`；根目录 `server/` 只作为历史参考，不再新建第二套身份或权限体系。
- C7 用户目录、教师审核、课程生命周期和认证审计已有 canonical 路由及测试。
- 当前工作区的 `A_task` 分支落后于 `origin/A_task`；上游已经包含账号恢复/创建、A4 全站审计读取、A7 AI 用量记录、临时访问授权和相应迁移。实现时优先复用并验证这些提交，而不是重写同一契约。
- Admin 页面已经集成在当前 Next.js 应用中，保留现有 `/admin/*` URL 和 `cidentity=real` / `governance=real` 功能开关；不额外创建重复的前端认证入口。

## 范围

### 目标（In scope）

1. 管理员专属用户目录、账号停用/恢复/创建和教师申请审核。
2. 课程草稿、发布、结束、邀请码和版本/理由校验。
3. 认证审计与全站业务审计的只读查询、脱敏详情和筛选分页。
4. AI 调用用量的真实记录、按日期/功能/模型聚合和管理员只读查询。
5. 临时只读访问申请、管理员审批、到期/撤销和实际读取权限检查。
6. 迁移、OpenAPI 类型、HTTP/数据库测试、前端 real 分支和部署配置。
7. 为新的 Railway 项目准备独立的 web/api/postgres/redis/worker 服务边界；不把凭据写入仓库。

### 非目标（Out of scope）

- 不重写已有学生/教师业务模块，不改变 Task、Evidence 或正式验收规则。
- 不创建第二个用户库、第二套 RBAC 或第二个后台 API。
- 不在没有真实 provider 数据时生成“零用量”、虚构趋势或伪造授权成功。
- 不把 Railway 服务创建、密钥配置或账号能力冒充为已完成；本轮项目与服务已在负责人授权的 workspace 建立并完成匿名部署验收，邮件、Google 和初始管理员仍需按真实凭据与受控流程配置。
- 不在本轮加入与 Admin 治理无关的视觉改版或动效。

## 核心业务与安全边界

- Admin 写操作必须经过当前 active 管理员、已验证学校邮箱、CSRF、版本（CAS）和理由校验；不能自停用或自批准访问。
- 账号、教师审核、课程和访问审批的状态变更使用现有服务事务和幂等记录；同一请求重放返回同一结果，内容变化返回冲突。
- 审计记录只追加不修改/删除；输出只包含允许的标量元数据，邮箱、凭据、会话、验证码和项目正文不进入管理日志。
- AI 结果永远标记为需要人工确认；用量记录失败不能影响业务调用，缺少真实用量时接口返回明确的 503。
- 临时访问授权只允许 read/project|task|evidence 范围，批准回执必须精确匹配申请人、资源和到期时间；每次实际读取仍重新检查有效授权。

## 方案比较与选择

### 方案 A：另起一个独立 Admin 服务（不采用）

单独创建 `apps/admin`、独立认证和一套 API。视觉上容易隔离，但会复制会话、用户、权限和审计逻辑，违反现有“统一 API/统一身份”边界，且会产生跨服务一致性风险。

### 方案 B：扩展现有 `services/api`（采用）

把 Admin 当作同一平台的治理角色，复用现有 `/api/v1/admin`、`/api/v1/c-admin`、`services/api/app/auth`、C7 服务和 PostgreSQL 迁移；已有上游实现先合入/验证，再补 provider 接线和剩余测试。前端继续使用现有 `/admin/*` 页面和 real feature flags。此方案改动最小、权限边界最清楚，也最适合课程演示和 Railway 独立环境部署。

### 方案 C：只保留 Mock 页面（不采用）

开发量最低，但不能证明真实服务端鉴权、数据持久化、审计和撤销语义，也无法支撑“完整后台”的说法。

## 部署决策

新 Railway 项目按服务边界准备：`web`、`api`、`postgres`、`redis`，需要异步任务时再启用 `worker`。Admin 页面暂时随 web 部署，API 仍是唯一业务后端。部署前必须配置 `APP_MODE/APP_ENV`、数据库/Redis 引用、`APP_ORIGIN`、HMAC/邮件/Google（若启用）等变量；所有 secret 仅存在 Railway Variables 或 GitHub Secrets。

## 验收标准

- Admin 非管理员、未验证管理员和失效会话均被服务端拒绝；前端隐藏不能替代服务端鉴权。
- 六个 Admin 页面在 real 模式下只消费真实 API；provider 未接通时显示明确不可用状态。
- 账号、教师审核、课程、审计、AI 用量、访问审批的成功/失败/冲突/重复提交路径均有可重复测试。
- Alembic 可升级到最新 head，旧迁移不被重写；API OpenAPI 与前端生成类型同步。
- `ruff check`、`ruff format --check`、API pytest、前端 lint/typecheck/build、路由检查通过；Railway 服务状态、匿名健康检查和未配置的身份/邮件能力在阶段报告中明确记录。
