# GroupProof 用户管理工作台设计

## 意图

把 `/admin/users` 从“按姓名查找并展开一条记录”的基础列表，提升为管理员每天可以快速判断、筛选和处理账号的用户目录工作台。页面延续本轮管理后台的浅色数据看板语言，但优先解决信息密度、状态可读性、处理路径和移动端可用性；真实数据、权限和审计规则保持不变。

## 当前问题

- 用户行只显示姓名和一串原始枚举，角色、账号状态、学校邮箱验证状态不易扫读。
- 详情在列表下方展开，处理一条记录时会失去列表上下文，桌面端需要滚动寻找操作区。
- 选中用户只存在 React 本地状态，刷新、复制链接或浏览器前进后退无法复现选择。
- 筛选没有重置入口、可见字段标签或快捷状态，错误信息缺少可诊断的下一步。
- 移动端只是把控件纵向排列，详情和操作没有适配为抽屉/底部面板。

## 目标

1. 管理员在一屏内看清当前筛选结果、角色、启用状态和邮箱验证状态。
2. 点击用户后在桌面右侧打开详情抽屉，列表保持可见；窄屏改为全宽底部/侧边面板。
3. 选中用户通过 `?user=<identity-id>` 写入 URL；关闭、换页、筛选和刷新遵循可复现规则。由于 C 目录没有按 ID 的详情接口，若刷新后该 ID 不在当前页/筛选结果，清除选择并说明原因，不展示猜测的旧详情。
4. 保留并强化现有新增、停用、恢复、教师审核、版本冲突和权限失效流程。
5. 所有统计只来自当前接口返回的真实结果：`data.total` 标为“结果总数”，页面内计数明确标注“当前页”，不把一页数据冒充全局统计。
6. 375px、768px、1024px 和桌面宽度下，核心筛选、查看、填写理由和提交操作都可用。

## 非目标

- 不把旧的只读 `/api/v1/admin/users` DTO 与 C 管理接口混用。
- 不修改账号数据库、角色模型、教师审核规则、CSRF、版本校验或通知语义。
- 不新增批量停用、批量改角色、密码重置或敏感字段展示。
- 不为了做 KPI 而新增虚构的登录次数、最近登录时间、活跃度或增长率。
- 不改变现有 `/admin/users` 和 `/admin/teacher-verifications` 路由。

## 约束与真实数据边界

- 用户目录继续调用 `cIdentityClient.users`，写操作继续调用 `create`、`disable`、`enable`；教师页继续调用 `applications`、`review`。
- C 管理目录每页最多 10 条，返回字段只有 `id`、`name`、`studentId`、`college`、`roles`、`status`、`version`、`schoolEmail`、`schoolEmailVerified`、`canDisable`。不从旧目录接口猜测用户名、创建时间或最近登录时间。
- `enabled/disabled` 映射为中文状态标签；角色枚举映射为中文标签；邮箱值和验证状态按后端返回原样展示。
- 管理员写操作仍要求当前会话、CSRF、已验证学校邮箱和匹配的 `expectedVersion`。任何失败都不能保留已失权用户的敏感详情。
- 页面 real 模式不回退 mock；接口错误、空数据和加载中状态必须各自可解释。
- 现有 C 目录没有学校邮箱验证过滤参数，因此“待验证”只作为当前页摘要，不作为伪装成全局结果的快捷筛选；快捷筛选仅包含全部、可用、已停用。

## 方案取舍

### 方案 A：密集表格优先

把用户展示为完整表格，点击“查看”仍在页面下方展开详情。实现成本最低、适合批量扫读，但详情仍会打断列表上下文，移动端需要横向滚动，不能解决当前主要痛点。

### 方案 B：用户目录 + 右侧详情抽屉（采用）

用真实字段组成可扫读表格：姓名/学号、学院、角色、账号状态、学校邮箱验证、操作。顶部放结果摘要、快捷筛选和新增/刷新；点击行写入 URL 并打开抽屉，抽屉内保留资料、版本提示、处理原因和停用/恢复按钮。桌面保持列表与详情并列，375–768px 抽屉变成全宽面板并固定操作区。它不需要改变后端契约，却同时解决上下文、可复现和操作效率问题。

### 方案 C：卡片式用户中心

每个用户使用大卡片展示，详情以全屏页面承载。视觉更接近营销型后台，但同一页能看到的用户更少，管理员处理多账号时效率低，也会重复已有首页卡片语言。

方案 B 与当前 API 和已有管理台最匹配，因此作为本次实现方案。

## 页面结构

### 标题区

- 标题“用户管理”和一句职责说明。
- 右侧固定“刷新列表”“新增账号”主操作；刷新时显示进行中状态。
- 下方显示“当前环境 · 数据来自身份服务”的轻量上下文。

### 结果摘要

四个小卡片：

- “结果总数”：当前筛选条件下接口返回的 `total`。
- “当前页可用”：当前页 `status=enabled` 的条数。
- “当前页已停用”：当前页 `status=disabled` 的条数。
- “当前页待验证”：当前页 `schoolEmailVerified=false` 的条数。

后三项必须带“当前页”字样，避免误解为全局统计；无数据时显示 `—` 或 `0`，不生成趋势。

### 筛选工具栏

- 可见标签的搜索框：姓名、邮箱或学号。
- 学院文本搜索、角色和账号状态下拉框。学院不改成静态下拉，避免遗漏后端已有或未来新增的学院值。
- “查询”“重置筛选”按钮。
- 一组可键盘操作的快捷筛选：全部、可用、已停用；快捷筛选与下拉筛选保持同一 URL 状态。
- 已生效筛选以可关闭的 chip 显示；关闭 chip 只移除对应参数并回到第 1 页。

### 用户目录

使用语义化表格和横向滚动容器。列顺序：

1. 用户：头像首字母、姓名、学号（无学号显示“未填写”）。
2. 学院。
3. 角色：中文 badge，可同时显示多个角色。
4. 账号状态：可用/已停用 badge，并显示文字。
5. 学校邮箱：邮箱文本 + 已验证/待验证 badge；长邮箱可断行。
6. 操作：`查看`，当前选中行有明确视觉和 `aria-selected`。

空状态仍使用“没有符合条件的记录”，同时提供“重置筛选”；加载中保留上一份列表并覆盖轻量 loading 状态，避免抽屉和表格闪烁。

### 详情抽屉

- `role=dialog`、`aria-modal=true`、唯一标题和关闭按钮；桌面宽度约 390–440px。
- 打开时焦点进入关闭按钮，`Esc` 和遮罩可关闭，关闭后焦点回到触发该行的“查看”按钮；Tab 不离开抽屉。
- 资料区展示姓名、学号、学院、角色、账号状态、学校邮箱和验证状态、当前版本。
- 账号状态和邮箱状态同时使用颜色与文字；`canDisable=false` 时显示“不能停用当前登录账号”的原因。
- 操作区固定在抽屉底部：处理原因文本框、确认停用/确认恢复；提交前需要非空理由。
- 发生版本冲突时保留理由并锁定按钮，提示“刷新列表后重新核对”；刷新成功只更新版本，不清除理由。
- 本轮抽屉改造只覆盖 `/admin/users`；教师审核保留现有申请 ID、历史快照和审核动作结构，后续另立设计，避免把申请 ID 与用户 ID 混在同一个 URL 参数中。

## 错误、权限与反馈

- 映射 `401/403/409/422/503/NETWORK_ERROR` 为中文可执行提示；能拿到 `requestId` 时显示请求编号。
- 列表错误旁提供“重试”；权限失效时清空目录和抽屉，不能把旧用户数据留在页面上。
- 创建表单保留输入并提供字段级错误；教师通过按钮禁用时明确提示需先验证学校邮箱。
- 成功反馈说明后端结果（包括站内通知是否接入），不把前端按钮点击当成成功。

## 验收标准

- `?q=...&role=...&status=...&college=...&user=...` 刷新后筛选和详情可复现；换页/重置筛选会清除 `user`。
- 表格不再输出原始 `student/teacher/ta/admin` 或 `enabled/disabled` 作为唯一用户可见文本。
- 桌面端详情打开时列表仍可见；窄屏无横向页面溢出，抽屉操作区可见且可滚动。
- `Esc`、关闭按钮和遮罩均可关闭详情，焦点返回触发按钮；键盘可完成筛选和提交。
- 既有 `e2e/c-identity-api.spec.ts` 的创建、停用、恢复、冲突、权限和 404 流程继续通过，并新增 URL 选择、状态 badge、重置筛选、抽屉关闭和移动布局断言。
- `node scripts/check-admin-pages.mjs`、相关 Playwright 测试、`npm run lint`、`npm run typecheck`、`npm run build`、`npm run check:routes` 通过。

## 实现时的明确决定

- 本次不扩展后端 DTO；如果未来需要全局角色统计、创建时间或最近登录时间，另立 API 变更和数据白名单设计。
- 优先在现有 `IdentityAdminApiPages.tsx` 与 `governance.module.css` 内实现；只有抽屉焦点管理、状态标签等确实可复用时才提取小组件。
- 现有按钮文案和操作契约保留，视觉改版不能让测试或管理员失去“新增账号、查看、处理原因、确认停用、确认恢复、通过、拒绝、取消、刷新列表、查询、重置、下一页”等入口。
