## 业务规则与状态

正式版本一经发布不可原地改写；编辑进入独立草稿，旧正式内容仍为执行依据。确认绑定 revisionId、contentVersion 和 memberRoster，内容或确认名单变化时旧确认失效。Project.baselineVersion/planVersion 表示当前生效版本，草稿版本单独保存。AI/证据的历史不因新增快照被删除。

## 数据与操作接口

```ts
export interface MemberConfirmation {
  userId: string;
  revisionId: string;
  contentVersion: number;
  confirmedAt: string;
}
export interface Revision<T> {
  id: string;
  projectId: string;
  number: number;
  version: number; // 实体并发版本，与内容版本分别递增
  contentVersion: number;
  status: "draft" | "confirming" | "published";
  payload: T;
  memberRoster: string[];
  confirmations: MemberConfirmation[];
  basedOnRevisionId?: string;
  legacy?: { confirmedUserIds: string[]; timestampUnknown: true };
}
export interface BaselinePayload {
  requirements: Requirement[];
  modules: FunctionalModule[];
  sourceFileIds: string[];
}
export interface PlanPayload {
  tasks: Task[];
  criteria: AcceptanceCriterion[];
  milestoneLinks: { taskId: string; milestoneIds: string[] }[];
}
export type BaselineRevision = Revision<BaselinePayload>;
export type PlanRevision = Revision<PlanPayload> & {
  baselineRevisionId: string;
};
```

补充 CourseRuleRevision（课程约束、模板快照、版本、发布者、时间、原因）、RuleChangeReview（projectId、前后规则版本、影响、确认人/时间）。MockData 增加这些集合及 schemaVersion。Project 增加 activeBaselineRevisionId、activePlanRevisionId、appliedCourseRuleRevisionId、sourceProjectId；新集合数据流与原实体共享稳定业务 ID。

## 实现步骤

1. 确定上述类型和默认值；追加字段兼容现有页面读取，保持 Requirement/Task 的业务 ID 稳定。
2. 为课程设置与模板定义结构化快照：截止日、组队方式/人数、必交材料、评分说明、GitHub/AI 条款、里程碑模板；保留旧 rules 文本用于展示。
3. 实现 migrateWorkspace(raw)，按 schemaVersion 逐步补齐集合和明确的旧字段默认值。
4. 已有 frozen 基线按当前对象建立初始历史快照并记录 legacy 来源；旧 confirmedBy 存入 legacy.confirmedUserIds，不生成缺少真实时间的新 MemberConfirmation。
5. 旧 planConfirmed=true 保留已发布状态，但历史确认注明未完整记录；后续编辑走新确认流程。
6. 内容修改增加 contentVersion 并清空确认；普通确认只增加实体并发 version，不改变内容版本。
7. 增加选择器读取 active revision/current draft，避免页面自己混用两个版本。

## 核心代码示例

```ts
export function confirmationsComplete<T>(revision: Revision<T>): boolean {
  if (revision.memberRoster.length === 0) return false;
  return revision.memberRoster.every(userId =>
    revision.confirmations.some(item =>
      item.userId === userId &&
      item.revisionId === revision.id &&
      item.contentVersion === revision.contentVersion
    )
  );
}
```

示例应在上述接口与现有代码中接入；接口定义片段不应被当作已经实现的服务。

## 页面接入与错误反馈

版本页区分“当前正式版本”和“待确认草稿”，显示每人确认状态与时间。迁移失败保留原始浏览器数据并报告格式错误，不自动覆盖为演示种子；没有保存数据时才初始化种子。

## 测试场景

- 迁移幂等；重复读取不增加版本或快照。
- 修改草稿不改变正式快照；确认旧 contentVersion 不计入完成。
- 重复个人确认不产生重复记录。
- 名单变化需要重新确认；未知旧时间不被伪造。
- 迁移前原始记录保留，缺少新字段的已有页面仍可读取。
