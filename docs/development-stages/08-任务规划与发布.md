## 业务规则与状态

计划草稿绑定已发布 baselineRevisionId；当前发布必须基于仍生效的基线。成员共同编辑草稿并确认自己的分配，确认绑定完整计划内容版本；暂无任务的成员仍确认当前无分配责任。组长发布/解锁；例外推进留原因与缺席名单，不绕过结构校验。默认沿用整数百分比权重：顶层合计100，子任务合计父权重。

## 实现步骤

1. 将任务编辑指向 PlanRevision.payload，提供明确的需求、模块、验收标准、负责人、里程碑与依赖选择。
2. 保存草稿时维护父子/需求/模块关联，增加 contentVersion，并清空其责任确认。
3. 实现独立 validatePlan：同项目引用、有效负责人、非空验收标准、整数权重、父子树合法、依赖无环。
4. 再生成建议只填未拆解的需求，以逻辑关联判重，所有建议仍是待人工编辑草稿。
5. 个人确认保存至版本记录；用确认进度面板替换本地布尔值。
6. 正常/例外发布执行同等结构约束，并原子生成当前 Task/AcceptanceCriterion 投影和正式计划快照。
7. 发布后树/看板/列表消费同一正式任务集合；解锁创建新草稿，旧历史保留。
8. 与任务执行、验收及贡献模块联调：版本变化/任务字段变化的失效标记及稳定 ID 按契约消费。

## 核心代码示例

```ts
function validateWeightTotals(tasks: Task[]): string[] {
  const errors: string[] = [];
  if (tasks.some(t => !Number.isInteger(t.weight) || t.weight < 0 || t.weight > 100))
    errors.push("任务权重需为 0–100 的整数");
  const roots = tasks.filter(t => !t.parentTaskId);
  if (roots.reduce((sum, t) => sum + t.weight, 0) !== 100)
    errors.push("顶层任务权重合计必须为 100%");
  for (const parent of tasks) {
    const children = tasks.filter(t => t.parentTaskId === parent.id);
    if (children.length && children.reduce((sum, t) => sum + t.weight, 0) !== parent.weight)
      errors.push(parent.id + " 的子任务权重合计需等于父任务权重");
  }
  return errors;
}
// validatePlan 还要执行归属、负责人、标准、树结构与依赖环校验。
```

## 页面接入与错误反馈

沿用任务树和侧栏表单风格，显示正式与草稿版本、校验错误定位、全员责任确认。新增任务选择实际关联，不静默默认第一条需求。保存/确认/发布分别反馈，发布权限与硬校验条件分别控制。

## 测试场景

- 顶层和子层权重错误、非整数、无负责人/标准均不能发布。
- 跨项目依赖、自引用、父子环和依赖环拒绝。
- 保存或基线变化使旧确认无效，刷新后确认状态仍存在。
- 非组长不能发布，缺确认正常发布拒绝，例外发布保留真实签名和原因。
- 树/看板/列表反映同一正式计划，无重复任务或悬空标准 ID。
