### 需要说明的设计决定

1. **分析在哪里跑（和计划不同，需要确认）**：计划写的是放进 `modules/tasks` 的 Celery 队列。但 worker（`services/worker`）是独立服务，拿不到 API 的数据库模型和 A 的 AI 函数。所以现在分析在 API 进程里、响应返回之后执行（FastAPI 后台任务），页面每 2 秒查一次状态。效果一样（先显示“处理中”，完成后显示结果），超过 15 分钟没结束的分析会在下次开始时标为失败。要改成 Celery，需要 worker 能访问数据库和 A 的 AI 模块，这要和负责 worker 的同学商量。
2. **来源标记放在 B 自己的表里**：计划写“需求加 `origin` 和 `edited_by_human`”。为了不改大家共用的 `requirements` 表（同 B-3 的原因：C 的迁移兼容测试会用旧表结构写数据），这两个标记放在 `b_requirement_meta`。
3. **重新分析保留哪些**：手工录入的、人工改过的 AI 需求、在冲突里被人处理过的需求都保留；只有没人动过的 AI 需求会被替换。人工改过的那条 AI 需求，下次分析不会再生成一条一样的出来。
4. **冲突怎么对到需求**：AI 返回的冲突只给出资料出处，B 按出处找到对应的两条需求再写进 `requirement_conflicts`；对不上的冲突跳过并在分析结果里计数。
5. **冲突处理的结果**：没被采用的那条需求不删除（保留历史），标记为“冲突处理后未采用”，不进入基线快照。
6. **基线状态**：`projects.setup_status` 的取值里没有 `baseline_frozen`，用的是已有的 `frozen`；等待确认期间是 `pending_confirmation`，这段时间所有初始化内容（包括 B-3 的基本信息和资料）都不能改，返回 `BASELINE_IN_CONFIRMATION`。
7. **谁提交基线**：只有组长能提交，提交即算组长本人已确认；其余每个组员各有一条确认。任何一人退回，这一版作废，项目回到草稿，可以修改后重新提交。
8. **通知和待办**：确认待办用 C 已有的 `baseline` 目标类型（待办分类 `task`），点开进项目初始化页。
