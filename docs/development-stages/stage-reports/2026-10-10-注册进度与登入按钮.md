## 任务范围

左侧「注册进度」四项的阶段配色与状态文案、阶段命名统一（“完成 / 教师审核”→“身份确认（学生/教师）”）、“账号安全”改可选阶段、总状态“完成注册”完成态、新增「登入」按钮（会话升级进入业务）；状态必须来自后端已保存/已验证的事实，教师身份仍需有效审核批准，侧栏/页面/按钮一致，会话轮换后 Cookie/CSRF 正确衔接，保留后端鉴权并复用现有组件。

## 实现内容

### 1–2 阶段底色与命名（`components/account-shell.tsx`、`app/globals.css`、`messages/*`）

- 四项顺序不变：基本资料（必填）、学校邮箱（必填）、**身份确认（学生/教师）**（必填，原“完成 / 教师审核”，第 3 页标题/面包屑/三语同步更名）、**账号安全（可选）**（第 4 项与对应页面统一“账号安全”，常驻“可选”小标签）。路由沿用 `/account/status`、`/account/security`。
- 整行底色（新增语义 Tokens `--gp-stage-*`，参考值 `#EAF2FF/#FEF2F2/#F3F4F6`，文字对比度 ≥ 4.5:1）：前三项完成=浅蓝 + 勾选图标 + “已完成”；未完成/跳过/未通过=浅红 + “待完成”（教师按事实显示“待提交/审核中/未通过”）；账号安全未完成=浅灰 + “可选”，完成=浅蓝 + 蓝色完成标识 + “已完成”。
- 状态不只靠颜色：每行有状态文字 + 图标；选中页用边框 + 左侧线 + 字重 + `aria-current="page"` 表达，与“已完成”分离（截图 03 可见选中行深蓝描边而完成行浅蓝底）；加载中中性占位（灰底、无状态文字、总状态“进度加载中…”），读取失败给“重试”按钮，未知状态绝不标完成。

### 3 完成条件与可选账号安全（`server/app/services/registration.py` 派生 + `features/account/registration-progress.tsx` 共用推导）

- 新增集中派生：`identityConfirmed`、`securityComplete`、`requiredCompletedCount`（只计前三项，总数 3）、`canEnterWorkspace`（与 `guard.require_active_user`/`sessions.cap_scope` 同口径）。完成状态只读 `/me` 注册 DTO 的后端事实（资料已保存校验、绑定学校邮箱已验证、教师有效审核批准），与页面访问顺序、点击、本地输入无关。
- 教师身份确认仍需有效审核批准：提交申请/看状态页/客户端选择“教师”都不算完成；批准由管理员接口真实授予（未改任何审核逻辑）。
- 账号安全（可选）：密码账户=可用密码凭据 + 登录邮箱已实际验证（含注册时即满足）；纯 Google=可信认证事实。不计入必填进度、不作为准入条件、不要求再改一次密码或绑定 Google。
- 历史账户边界（明示保留）：登录邮箱未验证的密码凭据不得借 active 取得 full 业务会话（既有规则“不能凭未经验证的邮箱接管历史账户”）；此时第 4 项显示浅灰“可选”、前三项仍可完成、“登入”保持可点击，但服务端不放行——点击后留在个人中心并解释 + 给出“账号安全”补验入口（见截图 05）。已验证 Google 身份不受另一条未验证密码凭据影响，可正常进入（pytest P5 覆盖）。

### 4 注册状态文案（侧栏与第 3 页共用同一推导与同一组件 `ProgressStatusChip`）

- 前三项全部完成：绿色完成态“**完成注册**”（替换旧黄色“待完善基本资料”）；否则按实际事实显示“待完善基本资料 / 待验证学校邮箱 / 待提交 / 审核中 / 审核未通过 / 账户已停用”（停用等异常不被“完成注册”覆盖）。
- 教师等待审核时提供“刷新审核状态”入口；`useMe`（按用户隔离的 react-query key）在窗口重新获得焦点时强制重读，保存/验证/审核变化后同步；退出/切换账号清空查询缓存。

### 5 「登入」按钮（`components/account-shell.tsx`、`server/app/routers/auth.py`）

- 位置：状态提示正下方。前三项任一未完成→灰色、真实 `disabled`（鼠标/键盘均不可触发），旁注“尚缺必填阶段：…”；前三项完成→绿底白字（`--gp-enter-bg: #15803d`，对比度 ≥ 4.5:1）可点击，账号安全灰色“可选”不影响。
- 点击显示“正在进入…”并防重复提交；调用 `POST /api/v1/auth/session/refresh` 服务端重新核验资格，必要时把 onboarding 会话升级/轮换为 full，然后进入 `/home`（或经 `sanitizeReturnTo` 校验的站内 returnTo）。审核/账户状态变化→留页解释并刷新进度；网络失败可重试（附请求编号）；401→引导重新登录。
- **修复会话缺陷**：`/api/v1/auth/session/refresh` 此前在轮换会话后只回 JSON、**不写回新 Cookie**，浏览器继续用已失效旧 Cookie + 旧 CSRF 必然断链；现与改密/验证等接口一致写回 `Set-Cookie` 并返回新 `csrfToken`，前端经 `AccountSessionProvider` 同步最新会话（旧 Cookie/旧 CSRF 在轮换后立即失效，pytest P3 验证）。
- 不通过 `router.push`/放宽 API 门禁/前端变量完成进入；业务 API（`require_active_user`）与资源权限保持不变。

## 遗留限制 / 未验证项

1. **教师“有效批准后变蓝并允许进入”仅服务端验证**（pytest P2/P2b 覆盖批准与驳回分支）；开发环境无管理员浏览器凭据，浏览器只验证了“待提交/审核中保持浅红且禁用”与“审核依据失效退回”。管理员浏览器流待 `check:auth-browser` 后续批次补充。
2. **历史账户（登录邮箱未验证）与“仍能进入”的取舍**：需求 5 写“账号安全尚未完成也能进入”，但同一文档要求“不能凭未经验证的邮箱接管历史账户/保留后端鉴权”。实现取安全侧：按钮可点击（不把第 4 项变成必填），但服务端不放行，点击后解释并给补验入口；补验完成后同一按钮经会话升级正常进入（R5 全流程实测）。
3. **dev 冷编译偶发水合超时**（无头浏览器时序问题，非功能缺陷）：`check-registration-progress` 已内置水合等待 + 重载重试；`check-auth-browser`/`check:browser` 在冷启动下可能首跑 flake（复跑通过）。生产构建不受影响。
4. **邮件通道**：本次浏览器验收按既有约定用 `MAIL_MODE=capture` 启动后端（验证码从本地捕获器读取）；`.env` 仍为上次交付的 `MAIL_MODE=smtp`（QQ 邮箱）。E21 真实收件仍未人工联调。
5. 小项：审核等待徽章沿用通用词条 `pending_verification`（显示“待验证”），措辞可再打磨；第 4 项完成态同时显示“可选”标签与“已完成”状态（保留需求的双通道标注）。
6. 本次顺带修复 2 个环境缺口：`BUSINESS_DATA_FILE` 此前只认环境变量不读 `.env`（业务接口 503，新增 `config.business_data_file` 字段）；`check:browser` 需 `NEXT_PUBLIC_APP_MODE=mock`（已记录于状态文档）。
