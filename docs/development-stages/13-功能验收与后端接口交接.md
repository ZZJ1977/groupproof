## 业务规则与状态

验收应覆盖权限资格、执行状态、版本、归属、持久化和异常恢复。功能阶段保持现有风格，必要响应式/无障碍/反馈同时完成。接口交接明确Mock与真实服务边界及待实施工作，浏览器角色切换不是生产鉴权。

## 数据与操作接口

按项目、基线、计划、课程规则、助教授权和文件整理接口表：操作名、目标、输入白名单、返回类型、资格、前置状态、expectedVersion、幂等语义、错误及关联变更。后端沿现有 FastAPI 方向提供适配，身份来自服务端会话；数据库用事务和版本条件更新，文件用对象存储与受授权读取。当前阶段交付契约，不虚构已部署的API URL或第三方调用。

## 实现步骤

1. 从待开发状态逐项核实01–12对应代码和依赖，确认通用CRUD迁移/跨模块命令消费情况。
2. 使用独立夹具与Node内置测试覆盖纯规则、版本与命令；不为本阶段额外引入通用测试框架。
3. 使用现有演示数据或可复现夹具走教师规则→创建→初始化→确认→计划→执行视图→规则变更→设置/重开。
4. 执行npm run lint/typecheck/build/check:routes；临时开发服务器中执行CHECK_HTTP=1 npm run check:routes。
5. 做键盘、保存/失败/重试、权限直接URL、桌面和窄屏检查，保留必要截图或操作记录。
6. 输出接口交接表与真实服务待办，记录确认、对象存储、AI异步分析、版本并发各自尚待后端落实。
7. 更新阶段索引和FRONTEND_STATUS，仅将有实际证据的阶段标为已完成。
8. 满足整体功能闭环与模型/接口基本稳定后，进入14设计规范任务。

## 核心代码示例


示例应在上述接口与现有代码中接入；接口定义片段不应被当作已经实现的服务。

## 页面接入与错误反馈

功能走查涵盖反馈、错误定位、焦点、只读入口和基本布局。页面返回200后，还要实际点击保存、确认与发布，核对数据及刷新恢复。确认无法在现有演示身份完成的场景时使用服务层夹具验证，并记录验证方式。

## 测试场景

- 账号×资源×操作矩阵、跨组/跨课程、助教授予/撤销及公开DTO。
- 正常与例外发布、旧确认、旧版本、硬约束及历史保留。
- 原子创建/复制、存储失败、重复提交、刷新恢复和迁移幂等。
- 真实规则差异与影响、资料版本、归档只读和重新开启。
- 视图同步、接口错误、未实现服务不会给出伪造成功反馈。
